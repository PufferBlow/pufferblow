# Pufferblow command/event protocol, version 1

One websocket carries everything a chat client does. The client sends **commands**; the server answers each with an **acknowledgment** (or an **error**) and pushes **events** to everyone who may see the change.

The wire format is defined by the pydantic models in `pufferblow/api/protocol/` and exported as `docs/protocol/v1/schema.json`. The files in `docs/protocol/v1/fixtures/` are the contract shared with every client: the backend tests validate each one, and `client-new` and `pypufferblow` keep byte-identical copies and parse them in their own test suites.

## Connecting

```
wss://<instance>/ws?protocol=1&auth_token=<token>
```

- `protocol=1` is required. The older un-versioned frames and the per-channel socket (`/ws/channels/{id}`) were retired; a connection without it is closed with code `1008`.
- Edit, delete and reactions on channel messages are commands only; the HTTP routes for them were removed. Sending with attachments, history, search and read markers stay on HTTP.
- The token is checked on connect and again on every `ping`, so an expired or revoked token ends the session (close code `4401`). Putting the token in the URL is a known weakness (it can reach logs); logs redact it, and a first-frame `auth` command is planned.
- A user may hold at most 10 protocol sockets. A user with no channels yet can connect and subscribe later.

The first server frame is `hello`:

```json
{"type": "hello", "version": 1, "supported": [1], "session_id": "ses_abc123", "epoch": "ep_1"}
```

`epoch` identifies this server process. It changes on restart; see [Delivery](#delivery).

## Envelopes

Every frame is a JSON object with `type` and `version: 1`.

| Direction | `type` | Fields |
|---|---|---|
| client → server | `command` | `id` (client chosen, unique per connection), `name`, `data` |
| server → client | `ack` | `id`, `data: {status: "completed", result, duplicate?}` |
| server → client | `error` | `id` (or `null`), `error: {code, message, retryable, retry_after?}` |
| server → client | `event` | `id` (`evt_…`), `name`, `channel_id?`, `seq?`, `epoch?`, `data` |

An `ack` means the work is **committed**, not merely accepted. Events for a change are sent after its ack. Heartbeats stay `{"type": "ping"}` / `{"type": "pong"}`.

A frame whose `version` the server does not support gets `UNSUPPORTED_VERSION`; unknown frames and unknown fields are ignored by clients so the protocol can grow.

## Commands

All `data` objects reject unknown fields.

| Command | `data` | `ack.result` |
|---|---|---|
| `message.create` | `channel_id`, `content` (≤ 20 000 and the instance limit), `sticker_ids?`, `nonce?` | `{message}` |
| `message.edit` | `channel_id`, `message_id`, `content` | `{id, channel_id, content, edit_count, last_edited_at}` |
| `message.delete` | `channel_id`, `message_id` | `{id, channel_id, deleted, already_deleted}` |
| `reaction.add` / `reaction.remove` | `channel_id`, `message_id`, `emoji` | `{message_id, channel_id, emoji, reactions, changed}` |
| `channel.subscribe` | `channel_id` | `{channel_id, subscribed, seq, epoch}` |
| `channel.unsubscribe` | `channel_id` | `{channel_id, subscribed}` |
| `events.resync` | `channel_id`, `limit?` (1–100, default 50) | `{channel_id, messages, seq, epoch}` |

Attachments are not part of `message.create`; files use the HTTP upload route. `message.delete` of a message that is already gone succeeds with `already_deleted: true`, so a retry after a lost ack is harmless.

### Message object

```json
{"id": "m_8f2a", "channel_id": "c_general", "author_id": "u_ada", "author_name": "ada",
 "author_avatar_url": null, "content": "Hello!", "attachments": [], "reactions": [],
 "created_at": "2030-01-01T10:00:00+00:00", "edit_count": 0, "last_edited_at": null}
```

### Idempotency

`message.create` takes a `nonce` (≤ 128 characters). The server remembers `(principal, command, nonce)` for 24 hours. Repeating a command with the same nonce returns the **original** result with `duplicate: true` and publishes nothing, so a client that never saw the ack can resend without risk. The same text with a *different* nonce is a second message. A resend while the first is still being processed waits for it. Generate a fresh random nonce per message and **reuse it on every retry of that message**.

## Errors

| Code | Meaning | `retryable` |
|---|---|---|
| `MALFORMED` | Not JSON, wrong envelope or shape | no |
| `UNSUPPORTED_VERSION` | `version` is not supported | no |
| `UNKNOWN_COMMAND` | No such command | no |
| `UNAUTHENTICATED` | Credential no longer valid | no |
| `PERMISSION_DENIED` | You may not do this (also bots without the scope) | no |
| `NOT_FOUND` | Missing, or not visible to you. Existence of private channels is never disclosed | no |
| `CONFLICT` | State changed underneath the command | maybe |
| `RATE_LIMITED` | Too many commands; `retry_after` seconds | yes |
| `PAYLOAD_TOO_LARGE` | Frame or content too big | no |
| `VALIDATION_FAILED` | A field is out of range, empty or too long | no |
| `INTERNAL` | Server fault; details are logged with a request id, never sent | yes |

Clients also raise `NOT_CONNECTED`, `DISCONNECTED` and `TIMEOUT` locally; all three are retryable. Commands are rate limited per connection and per principal with token buckets.

## Events

| Event | `data` |
|---|---|
| `message.created` | message object |
| `message.updated` | `{id, channel_id, content, edit_count, last_edited_at}` |
| `message.deleted` | `{id, channel_id, deleted_by}` |
| `reaction.added` / `reaction.removed` | `{message_id, channel_id, user_id, emoji, reactions}` |
| `channel.created` | `{channel_id, channel_name, channel_type, is_private}` (no `seq`; see below) |
| `channel.updated` | `{channel_id, channel_name, is_private}`, or `{channel_id, deleted: true}`, or `{channel_id, access: "revoked" \| "granted"}` |
| `presence.changed` | `{user_id, status, source, at}` (no `channel_id` or `seq`) |
| `notification.created` | the notification (sent only to its recipient) |

On connect the server subscribes you to every channel you can see: public channels, and private ones you hold `view_private_channels` for or were added to. Access changes are applied to open connections without a reconnect:

- A channel is created, made public, or shared with you: you are subscribed and receive `channel.created` (new channel) or `channel.updated` with `access: "granted"`. Refetch the channel list to show it.
- A channel is made private, or you are removed from it: the subscription is dropped and you receive `channel.updated` with `access: "revoked"`. Private channels are also re-checked at delivery time.

These access notices carry no `seq`: they are about your connection, not the channel's history. `channel.subscribe` is still available for a channel you know of but are not subscribed to.

## Delivery

Events are delivered **at least once, in order per channel within one epoch**, after the change is committed. Each channel event carries a `seq` that increases by one per channel and the process `epoch`.

A client should:

1. Ignore an event whose `id` it has already handled.
2. Track the last `seq` per channel. A **gap** (`seq` greater than last + 1), or an **epoch** that differs from the one in `hello`, means events were missed: call `events.resync` for that channel and replace its recent window with the result, which also reports the current `seq` and `epoch` as the new baseline.
3. After a reconnect, resync every channel it is showing.

Sequence numbers live in memory, so they restart with the process; the epoch change is what tells clients. A crash between a commit and its publish loses the event, which resync recovers. There is no outbox.

## Bots

A principal is a user or a bot. A bot's privileges are its owner's **intersected** with its scopes (`send_messages`, `view_private_channels`), so it can never exceed its owner. Tokens look like `pbb_<prefix>.<secret>` and only a SHA-256 hash is stored. A bot opens a session with its token as `auth_token`, and may create, edit and delete messages; a bot-authored message is stored under its owner with `sender_bot_id` set, and only that bot (not its owner) may edit it. Bots cannot react yet.
